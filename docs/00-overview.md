# AIAKILOV CRM — אפיון על

> סטטוס: **טיוטה לאישור** · גרסה 0.1 · 2026-09-09

## 1. מטרת המערכת

CRM ייעודי לניהול מחזור החיים של תלמיד בקורסי AI:

```
ליד גולמי → יצירת קשר → כשירות (qualification) → הצעה → הרשמה → תשלום → לימודים → בוגר
```

המערכת אינה CRM גנרי. היא בנויה סביב **מחזורי קורס (cohorts)** עם תאריך פתיחה קשיח,
מספר מקומות מוגבל, ומדרון נשירה לפני תחילת הקורס. זה מכתיב שלושה דגשים שאין ב-CRM רגיל:

1. **דחיפות תלוית-זמן** — ליד שווה פחות ככל שמתקרבים לפתיחת המחזור ופחות מכך אחריה.
2. **קיבולת** — יעד המכירה אינו "כמה שיותר" אלא מילוי מדויק של N מקומות.
3. **סיכון נשירה** — נרשם ששילם מקדמה ולא השלים תשלום הוא נכס בסיכון, לא עסקה סגורה.

## 2. משתמשי המערכת (Personas)

| Persona | תפקיד | צורך עיקרי | מדד הצלחה |
|---|---|---|---|
| **נציג מכירות** | עובד על לידים | "עם מי לדבר עכשיו" | לידים/יום, יחס המרה |
| **ראש צוות מכירות** | ניהול נציגים | חלוקת לידים, מעקב ביצועים | עמידה ביעד מחזור |
| **רכז אקדמי** | ניהול תלמידים ומחזורים | מצב הרשמה, נוכחות, נשירה | תפוסת מחזור |
| **הנהלת חשבונות** | תשלומים | גבייה, חובות פתוחים | DSO, אחוז גבייה |
| **מנהל / Admin** | הכל | תמונת מצב, הרשאות | ARR, CAC, LTV |

## 3. תחומי הגדרה (Bounded Contexts)

הפרדה זו היא הבסיס למבנה הקוד — כל context הוא מודול עצמאי בשרת ובלקוח.

| Context | אחריות | ישויות ליבה |
|---|---|---|
| `identity` | משתמשים, תפקידים, הרשאות, סשנים | `user`, `role`, `permission` |
| `catalog` | קורסים ומחזורים | `course`, `cohort` |
| `pipeline` | לידים ותהליך המכירה | `lead`, `lead_stage`, `assignment` |
| `enrollment` | הרשמות ותלמידים | `student`, `enrollment` |
| `billing` | תשלומים וחיובים | `payment_plan`, `payment`, `invoice` |
| `workflow` | משימות ותזכורות | `task` |
| `engagement` | טיימליין, הערות, מסמכים, התראות | `activity`, `note`, `document`, `notification` |
| `intelligence` | AI, scoring, המלצות | `lead_score`, `ai_interaction` |
| `platform` | audit, logs, דוחות, הגדרות | `audit_log`, `report`, `saved_view` |

## 4. החלטות מוצר

### סגורות (אושרו 2026-09-09)

| החלטה | נבחר | השלכה |
|---|---|---|
| **Multi-tenancy** | `org_id` בכל טבלה מהיום הראשון | כל טבלה, כל מדיניות RLS וכל שאילתה כוללות `org_id`. הממשק אינו חושף בורר ארגון. [ADR-004](adr/004-multi-tenancy.md) |
| **שפת ממשק** | עברית בלבד, RTL | CSS ב-logical properties בלבד; `Intl` עם `he-IL`; פרומפטים בעברית. ללא שכבת i18n — שדות טקסט אינם מתורגמים. |
| **תשלומים** | רישום בלבד | המערכת רושמת תשלומים שבוצעו במקום אחר ומחזיקה אסמכתה. **אין נתוני כרטיס אשראי במערכת** — ולכן אין חשיפת PCI-DSS. |
| **WhatsApp** | יצירת טקסט בלבד | AI מייצר טיוטה; שליחה דרך העתקה או `wa.me`. ללא WhatsApp Business API, ללא תלות באישור Meta. |

שלוש מההחלטות האחרונות מצמצמות את היקף ה-MVP בצורה משמעותית — הן מסירות
compliance של PCI, אישור Meta, ושכבת i18n שלמה. הנתיב להרחבה בהמשך פתוח בכולן.

### פתוחות (לא חוסמות את M0–M3)

- 🟡 **מקורות לידים** — מאיפה לידים נכנסים? (טופס באתר, Facebook Lead Ads, ידני, CSV)
  קובע אילו integrations נדרשים. נדרשת תשובה עד תחילת **M4**.
- 🟡 **SSO ארגוני** — האם נדרשת התחברות דרך Google Workspace? נדרשת תשובה עד תחילת **M1**.
