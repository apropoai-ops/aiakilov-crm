# אסטרטגיית בדיקות

## 1. עיקרון

הדרישה היא "בדיקות לכל מודול". התרגום המעשי: **הבדיקה חייבת להיות מסוגלת להיכשל
מסיבה אמיתית.** בדיקה שמוודאת ש-mock הוחזר אינה בודקת דבר, אבל היא כן מייצרת מספר
כיסוי מרשים. לכן היעד הוא לא אחוז — הוא רשימת התרחישים שחייבים להיות מכוסים.

## 2. פירמידה

| רמה | כמות יחסית | מהירות | מה נבדק |
|---|---|---|---|
| Unit | ~60% | ms | לוגיקה טהורה: scoring, מעברי סטטוס, חישובי כסף |
| Integration | ~30% | שניות | service + DB אמיתי (Postgres ב-Docker) |
| API | ~8% | שניות | חוזה, authz, שגיאות |
| E2E | ~2% | דקות | 5 מסלולים קריטיים בלבד |

**אין mock ל-Postgres.** בדיקות integration רצות מול Postgres אמיתי מ-`supabase start`.
SQLite-כתחליף היה מסתיר בדיוק את מה שחשוב: RLS, טיפוסים, constraints, התנהגות טרנזקציות.

## 3. תרחישים שחייבים בדיקה

### RLS — הקטגוריה הקריטית ביותר

לכל טבלה עם `org_id`:

1. משתמש מארגון A **אינו** רואה שורה של ארגון B.
2. נציג ללא `lead.read.all` רואה רק לידים שלו.
3. `INSERT` עם `org_id` של ארגון אחר נדחה.
4. `UPDATE` על שורה של ארגון אחר משפיע על 0 שורות.
5. שורה שנמחקה רכות אינה מופיעה.

זו בדיקה שנכתבת פעם אחת כ-parametrized fixture ורצה על כל טבלה. טבלה חדשה ללא
מדיניות RLS מפילה את ה-build אוטומטית — יש בדיקה שסורקת את `pg_tables` ומוודאת
ש-`rowsecurity = true` על כל טבלה ב-`public`.

### מרוצי תנאים

- שתי הרשמות במקביל למקום אחרון במחזור → אחת מצליחה, אחת מקבלת `capacity_exceeded`.
- שתי בקשות `POST /leads/{id}/convert` עם אותו `Idempotency-Key` → הרשמה אחת.
- שני `PATCH` על אותו ליד → השני מקבל `412`.

### כסף

- סכום התשלומים בתוכנית = `total_amount` בדיוק (`numeric`, לא `float`).
- החזר לא עולה על ששולם.
- מטבעות מעורבים נדחים.

### AI

- `FakeLLMProvider` דטרמיניסטי — אין קריאות רשת ב-CI.
- פלט שאינו תואם סכימה → `filtered`, לא קריסה.
- ניסיון prompt injection בהערת ליד → לא משנה התנהגות.
- חריגה מתקרת עלות → הפיצ'ר מושבת בהודעה ברורה.
- Scoring: אותו קלט → אותו ציון (רפרודוקטיביות).

### Frontend

- כל קומפוננטה: 5 המצבים (loading / empty / empty-filtered / error / data).
- מלכודת פוקוס ב-modal, `Esc` סוגר, פוקוס חוזר.
- ניגודיות בשני הנושאים — `axe-core` ב-CI.
- RTL: צילום מסך משווה בעברית ובאנגלית.
- טבלה עם 10,000 שורות מתחת ל-100ms.

## 4. E2E — חמישה מסלולים

1. התחברות → דשבורד נטען עם נתונים.
2. יצירת ליד → שיוך → שינוי סטטוס → המרה לתלמיד → הרשמה נוצרה.
3. יצירת תוכנית תשלום → סימון תשלום → פיגור מופיע בגבייה.
4. נציג מנסה לגשת למסך הגדרות → נחסם.
5. חיפוש גלובלי מוצא ליד לפי טלפון חלקי.

יותר מזה = חבילת E2E שבירה שהצוות מתחיל להתעלם ממנה.

## 5. שער CI

```
lint (ruff, eslint, stylelint)
  → typecheck (mypy --strict, jsdoc types)
  → import-linter (חוק השכבות)
  → unit
  → integration (Postgres בקונטיינר)
  → api contract (OpenAPI drift)
  → security (bandit, pip-audit, npm audit)
  → a11y (axe)
  → perf budget (lighthouse-ci)
  → e2e (playwright)
```

merge נחסם על כשל בכל שלב. אין `--no-verify`.

## 6. נתוני בדיקה

Factories (`factory_boy`), לא fixtures של JSON. Seed דטרמיניסטי.
כל בדיקה בטרנזקציה שמתגלגלת אחורה — אין תלות בסדר הרצה.
